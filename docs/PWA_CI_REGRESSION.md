# PWA 브라우저 테스트 대기 안정화

관련 이슈: #25. 실패 실행: [dev CI](https://github.com/Bin-925/job-application-tracker/actions/runs/36392442401).

## 관측한 사실

PR #23·#24의 필수 CI는 통과했지만 병합 후 dev에서 네 번째 브라우저 테스트가 제한 시간에 도달했다. 실패 위치는 오프라인 복귀 후 `navigator.serviceWorker.ready`와 `registration.update()`를 함께 기다리는 부분이었다. 테스트는 이 시점에 저장 API 응답을 의도적으로 붙잡고 있었다. API fixture는 테스트가 해제하기 전까지 응답하지 않는다.

trace에는 오프라인 요청 실패와 재연결 후 요청이 기록되었지만, 위 두 Promise 중 정확히 어느 내부 단계가 지연됐는지는 분리되어 있지 않았다. 따라서 앱의 저장 오류나 특정 Chromium 내부 결함으로 단정하지 않는다. 로컬 원본 시나리오 10회 반복 및 초기 manifest 응답 지연 실험에서는 같은 실패를 재현하지 못했다.

## 바꾼 검증 순서

1. 초기 worker 객체의 존재가 아니라 `active.state === 'activated'`를 polling으로 확인하고 최초 `ready`까지 기다린다.
2. 업데이트 요청은 이미 확인한 registration으로 수행해 실패 단계가 드러나도록 한다.
3. 오프라인 저장 실패·재연결을 확인한 다음 새 버전의 waiting 상태를 먼저 만든다.
4. 그 후 저장 요청을 붙잡고 업데이트 버튼이 비활성화되는지 검사한다. 저장 응답 해제 뒤 활성화를 확인한다.

이는 앱 코드를 변경한 것이 아니라, 여러 네트워크 수명주기를 하나의 무기한 대기에 엮었던 테스트 fixture 순서를 명시한 변경이다. 임의 sleep·재시도 옵션·검사 생략·timeout 확대는 해결책으로 넣지 않았다. 저장 중 새 입력이 생기는 활성화 경합은 기존 상태 전이 단위 테스트에서도 검사한다.

브라우저 테스트의 실패 trace는 CI Artifact에 남긴다. 반복 로컬 실행, PR CI 및 병합 후 dev CI를 모두 확인하고, 나중에 같은 문제가 관측되면 단계별 증거를 바탕으로 다시 진단한다.

같은 `dist`와 `test-results`를 사용하는 빌드·브라우저 검사는 직렬로 실행해야 한다. 이번 로컬 점검에서 반복 검사와 재빌드를 겹쳐 실행했을 때 산출물 교체로 MIME 오류와 trace 파일 충돌이 발생했으며, 이 실행은 안정성 통계에서 제외하고 고정된 빌드로 다시 검사했다.
