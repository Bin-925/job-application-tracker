# 로컬 PostgreSQL 백업과 복원 검증

2026-10-04: 영구 개발 DB의 로컬 백업과 격리 복원을 실행했다. 외부 보관·정기 예약·실제 DB 덮어쓰기 복구는 별도 단계다.

## 한 번에 백업하고 검증하기

PowerShell 7 이상과 Docker Desktop Linux 엔진이 필요하다. 실제 개발 컨테이너 `jobtracker-postgres`가 실행 중이어야 한다. 저장소 루트에서:

```powershell
./scripts/Backup-Postgres.ps1
```

기본 저장 위치는 `.local/backups`다. 실행마다 UTC 시각과 임의 ID를 붙여 이전 파일을 덮어쓰지 않는다. 외부 서비스에 업로드하지 않는다.

| 파일 | 의미 |
|---|---|
| `jobtracker-시각-ID.dump` | PostgreSQL custom-format 백업 |
| `…dump.backup.json` | 생성 시각, 파일 크기, SHA-256, 도구 버전 |
| `…dump.restore.json` | 해당 SHA-256의 복원 검증 성공 기록 |

**dump 파일만 있다고 검증 성공한 것은 아니다.** 명령이 오류 없이 끝나고 복원 성공 기록의 해시가 백업과 맞아야 한다. 실패 시 완성된 덤프/메타데이터는 원인 확인을 위해 남길 수 있지만, 성공 기록은 새로 발급하지 않는다. 예전 성공 기록은 그때 기록된 해시에만 유효하다.

기존 백업을 다시 확인할 때:

```powershell
./scripts/Verify-PostgresBackup.ps1 -BackupPath '.local/backups/실제파일명.dump'
```

원래 DB 주소나 대상 URL을 입력하는 옵션은 없다. 복원은 항상 새로 생성한 `jobtracker-restore-…` 컨테이너의 `jobtracker_restore` DB에서만 실행한다.

## 무엇을 보존하고 제외하나

- 회원, 암호화 해시로 저장된 비밀번호, 지원, 일정, 수정 버전, 관계/제약/인덱스, identity sequence, Flyway 변경 이력을 보존한다.
- `spring_session`과 `spring_session_attributes`의 **테이블 구조만** 보존한다. 로그인 세션 내용은 제외해 복원으로 과거 로그인 권한이 되살아나는 것을 막는다. 복구 후에는 다시 로그인해야 한다.
- DB 관리자/앱 계정 비밀번호 파일과 서버 역할 자체는 덤프에 들어가지 않는다. `.local/postgres`의 자격증명도 안전하게 별도 보관해야 한다.
- 원본에서는 `pg_dump`만 수행한다. 테이블 삭제, 행 변경, 시퀀스 증가, 원본 세션 무효화를 하지 않는다. pg_dump는 일관된 스냅샷을 사용하지만 서버 자원과 테이블 잠금은 사용하므로 마이그레이션과 동시에 실행하지 않는 편이 좋다. [PostgreSQL 공식 문서](https://www.postgresql.org/docs/17/app-pgdump.html)

## 검증 순서

```mermaid
flowchart LR
    A[실제 개발 DB 읽기] --> B[세션 제외 dump]
    B --> C[파일 크기와 SHA-256 기록]
    C --> D[외부 연결 없는 새 임시 DB]
    D --> E[단일 트랜잭션 복원]
    E --> F[데이터 구조와 시퀀스 검사]
    F --> G[임시 컨테이너 제거]
    G --> H[복원 성공 기록 발급]
```

덤프를 복원할 때 오류 하나라도 있으면 실패 처리한다. 필수 테이블, 빈 로그인 세션 테이블, 유효한 제약, 소유 관계의 고아 행 여부, 다음 ID가 기존 최댓값보다 큰지 확인한다. 시퀀스를 증가시키는 검사는 **복원본에서만** 한다.

복원본의 회원/지원/일정 개수와 테이블별 비교용 digest를 기록한다. 고정된 합성 데이터 테스트에서는 원본과 digest를 비교해 한글·메모 줄바꿈·날짜·버전까지 보존되는지 확인한다. 실제 사용 중 DB에서는 백업 이후 행이 변경될 수 있으므로, 나중에 읽은 원본 개수와 단순 비교하여 무결성을 주장하지 않는다.

Flyway 이력이 있으면 실패 이력이 없는지 검사하고 버전/체크섬을 기록한다. 이는 현재 애플리케이션의 Flyway validate 또는 API 전체 테스트를 대체하지 않는다. 직접 SQL로 만든 합성 fixture에는 가짜 Flyway 이력을 넣지 않는다.

## 안전 장치와 한계

- 로컬 Docker 엔진만 허용한다. 원본은 이름과 소유 라벨을 검사한 개발 DB 또는 자동 테스트 fixture로 한정한다.
- 복원 컨테이너에는 호스트 포트, 호스트 폴더, 원본 데이터 볼륨, Docker 소켓을 연결하지 않는다. 네트워크도 `none`이다.
- PostgreSQL 17, DB tmpfs 512MiB, 메모리 768MiB, CPU 1개, PID 256개로 제한한다. 검증 파일 크기는 최대 256MiB이며 더 큰 DB는 별도 자원 설계가 필요하다.
- 복원용 덤프는 임시 컨테이너의 쓰기 레이어에 복사하고 검증 후 컨테이너와 함께 제거한다. DB 데이터는 tmpfs를 사용한다. 디스크의 물리적 보안 삭제를 보장하는 기능은 아니다.
- dump/restore 명령에는 시간 제한을 두고, 실패 시에도 임시 컨테이너를 정리한다. Docker 자체가 고장 나 정리에 실패하면 수동 확인이 필요하며 성공으로 표시하지 않는다.
- Windows에서는 백업 폴더/파일의 ACL을 현재 사용자와 SYSTEM으로 제한한다. Linux CI에서는 디렉터리 700/파일 600을 사용한다. 프로젝트/디스크 루트와 프로젝트 상위 폴더를 백업 디렉터리로 지정하지 못하게 한다.
- `.local`과 덤프/결과 확장자는 Git에서 제외한다. **파일 자체는 암호화되지 않는다.** 계정·지원 기록이 담겨 있으므로 공개 업로드하거나 채팅에 첨부하지 않는다.
- SHA-256은 우발적 파일 변경을 찾는 수단이다. 덤프와 메타데이터를 함께 바꿀 수 있는 공격자를 인증하는 전자서명은 아니다. 신뢰할 수 있는 본인 백업만 입력한다.
- 덤프 복원은 원본 관리자가 정의한 SQL 코드를 실행할 수 있다. 격리된 검증 환경도 출처를 신뢰할 수 없는 덤프를 무조건 안전하게 만드는 장치는 아니다. [pg_restore 공식 주의 사항](https://www.postgresql.org/docs/17/app-pgrestore.html)
- 백업과 실제 데이터가 같은 디스크에 있으므로 디스크 고장·랜섬웨어에 대비한 별도 사본이 아니다. 외장/원격 암호화 보관과 주기·보존 기간은 이후 결정한다.
- 자동 삭제와 정기 예약은 아직 설정하지 않았다. 현재는 **한 명령으로 백업과 복원 검증을 자동 실행**하는 단계다.

## 회귀 테스트

```powershell
./tests/backup/Test-Backup.ps1
```

합성 PostgreSQL에서 원본 세션/행이 유지되는지, 덤프의 행 값이 복원되는지, 세션이 제외되는지 확인한다. 손상된 덤프, 없는 메타데이터, 세션이 포함된 덤프, 위험한 출력 디렉터리, 뒤처진 ID 시퀀스는 거부되어야 한다. GitHub Actions의 `PostgreSQL migrations and sessions` 작업에서도 같은 스크립트를 실행한다.

## 실제 복구는 별도 승인 단계

이 도구는 원본을 덮어쓰지 않는다. 실제 장애 때는 백업 시각과 손실 가능 구간을 확인하고, 새 영구 DB 및 앱 계정을 준비해 복원한 뒤 애플리케이션 마이그레이션/권한/API를 검증하고 연결을 전환해야 한다. 관리자 계정으로 실행한 임시 복원 성공만 보고 운영 계정/권한까지 복구됐다고 판단하지 않는다.
