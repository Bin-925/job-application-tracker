# 취준노트 발전 전략

검토 기준: 2026-09-23 첨부 ZIP. 목표: 실사용 완성도와 취업 포트폴리오, PWA 및 원스토어 출시.

## 1. 제품의 중심

제품이 해결할 문제를 다음처럼 제안한다.

> 여러 채용 사이트에서 진행하는 지원을 모으고, 지금 해야 할 행동과 중요한 일정을 놓치지 않도록 돕는다.

여기서 사용자 가치는 세 가지다. 입력과 재확인에 드는 시간 절약, 다음 행동의 명확성, 일정 누락 감소다. 기능을 추가할 때 이 중 무엇을 개선하는지 먼저 적는다.

엑셀이나 일반 캘린더와의 차이는 지원 상태와 일정이 연결된다는 점에서 만들어야 한다. 예를 들어 지원이 완료되면 지원 마감 알림을 중단하고, 면접이 변경되면 기존 알림을 취소하고 새 일정으로 바꾼다. 홈 화면도 단순 총계 외에 오늘 처리할 일과 가까운 일정을 우선 보여주는 방향을 검토한다.

포트폴리오 가치에는 학습 목적도 포함한다. 다만 'Java/Spring을 익히고 채용에서 설명할 경험을 얻기 위해 선택했다'와 '이 제품은 Java여야만 한다'를 구분한다. 기술의 필요성은 유일한 정답임을 증명하는 일이 아니라, 주어진 제약에서 비용과 효과를 설명하는 일이다.

## 2. 현재 구현과 문서의 차이

아래의 '확인'은 코드 존재를 뜻하며 실행 성공을 보장하지 않는다.

| 항목 | 확인한 상태 | 근거 |
|---|---|---|
| 인증/인가 | JWT 로그인과 회원별 지원 소유권 검사 | `backend/.../security/`, `service/ApplicationService.java` |
| 지원 기록 | CRUD, 상태 변경, 통계 API | `ApplicationController`, `ApplicationService`, `ApplicationRepository` |
| 화면 | 홈, 캘린더, 상세/등록/수정, 계정, 테마 | `frontend/src/pages/` |
| 검색/정렬 | 전체 목록을 받은 뒤 프론트에서 처리 | `HomePage.jsx:127` 부근 |
| 알림 | 페이지를 열어 조회한 목록에서 오늘부터 3일 이내 날짜 계산 | `frontend/src/utils/notifications.js:4` |
| 테스트 | 서비스 테스트, MockMvc 통합 테스트, 컨텍스트 테스트 | `backend/src/test/` |
| CI | 백엔드 테스트 작업만 정의됨 | `.github/workflows/ci.yml` |
| PWA/Android | manifest, service worker, Android 프로젝트 확인 안 됨 | 파일 목록과 소스 검색 |

| EC2/Docker | PRD에 전환 계획은 있으나 Dockerfile/배포 구현 확인 안 됨 | PRD와 파일 목록 비교 |

`README.md`, `PRD.md`, `AI_COLLABORATION.md`에는 `JobSearchProvider` 및 API 구현체 교체 경험이 서술되어 있다. 이 사본에서는 관련 코드를 찾지 못했다. 다른 브랜치나 자료에 존재할 가능성을 열어두고, 확인 전에는 완료된 성과로 사용하지 않는다.

PRD의 Railway 중지 상태, README의 라이브 배포 상태 역시 당시 기록이다. 현재 운영 상태를 별도로 확인해야 한다.

## 3. 현재 스택을 어떻게 설명할 것인가

아래는 현재 구조에서 도출한 유지 근거와 제안이다. 문서로 확인되지 않은 최초 선택 동기를 대신 만들어낸 것이 아니다.

| 선택 | 현재 프로젝트에 연결되는 이유 | 대안과 비용 / 재검토 조건 |
|---|---|---|
| Java 21 | 회원, 지원 상태, 일정 같은 도메인을 타입으로 표현하고 Java 백엔드 역량을 쌓는다. 기존 record DTO와 enum을 활용하고 있다. | Kotlin, TypeScript 백엔드도 가능하다. Java 21 자체가 필수 기능 때문에 선택됐다는 근거는 없다. 버전은 호환성과 지원 계획을 별도 기록한다. |
| Spring Boot | HTTP API, 검증, 인증, 트랜잭션, 테스트를 한 생태계 안에서 구성한다. 현재 계층 구조를 유지해 수정 범위를 예측하기 쉽다. | 작은 서비스에는 더 단순한 프레임워크도 가능하다. 메모리, 시작 시간, 배포 비용을 실제 환경에서 확인한다. |
| Spring Security / BCrypt | 인증 처리와 비밀번호 해싱을 직접 구현하지 않고 검증된 구성 요소를 사용한다. | 필터와 접근 정책은 직접 이해하고 테스트해야 한다. BCrypt는 복호화하는 암호화가 아니라 단방향 해싱이다. |
| JWT | 웹과 향후 Android에서 같은 API에 bearer 인증을 전달할 수 있고, 현재 구현을 활용한다. | 세션도 가능하다. 저장 위치, 만료, 갱신, 폐기 비용이 있다. '프론트/백 도메인이 다르므로 JWT가 필수'라는 기존 설명은 수정할 필요가 있다. |
| JPA | 회원-지원 관계와 반복 CRUD, 트랜잭션 처리를 단순화한다. | SQL, FK, 조회 횟수, 지연 로딩과 DB 차이는 남는다. 복잡한 집계가 필요해지면 필요한 쿼리만 명시한다. |
| PostgreSQL | 회원별 관계와 정합성이 중요한 데이터에 관계형 DB가 맞고, 기존 운영 구성을 이어갈 수 있다. | 현재 요구사항은 MySQL로도 충족 가능하다. 이 서비스가 PostgreSQL만의 기능을 필요로 한다고 주장하지 않는다. |
| JavaScript / React | 폼, 상태 전환, 캘린더 등 상호작용 화면을 구성하고 기존 웹 UI를 재사용한다. JavaScript의 초기 속도 이점은 가능성일 뿐 실제 최초 동기는 확인이 필요하다. | Vue 등도 가능하다. 상태와 API 계약이 늘면 TypeScript 도입을 검토한다. React 19 고유 기능을 활용했다는 증거는 확인되지 않았다. |
| Vite | 기존 SPA의 개발 서버와 번들링을 맡는다. 로그인 후 사용하는 도구라 현재 SSR 도입 필요성은 낮다. | 실제 개발/빌드 속도는 측정 전 수치를 주장하지 않는다. 공개 채용 콘텐츠의 검색 노출이 핵심이 되면 별도 검토한다. |
| Tailwind | 반복되는 상태 배지, 폼, 다크 모드 스타일을 일관되게 조합한다. | CSS Modules도 충분하다. 클래스 반복이나 디자인 불일치가 커지면 공통 컴포넌트와 토큰을 정리한다. |
| React Router / Axios | 화면 이동과 인증 헤더를 붙이는 API 호출을 공통 처리한다. | 브라우저 fetch도 가능하다. 현재는 인증 실패 처리가 공통화되지 않아 보완이 필요하다. |
| Gradle / pnpm | 기존 Java 빌드와 JS 의존성 관리를 재현한다. wrapper와 lockfile을 유지한다. | Maven/npm 대비 제품상 필수성은 없다. 도구 추가보다 버전 고정과 CI 재현성이 중요하다. |
| OpenAPI / 테스트 / CI | API 계약을 설명하고 회원 간 데이터 접근 같은 중요한 행동을 회귀 검증한다. | 테스트 존재와 실제 통과, 배포 전 검증 강제 여부를 구분한다. 프론트 검사와 배포 연결은 추가 확인 대상이다. |
| Vercel / Railway | 기존 기록상 초기 배포 경험과 인프라 관리 부담 절감을 위한 선택이다. | 현재 비용/가용성은 미확인이다. EC2 이전은 비용, 운영 학습, 복구 능력 개선 목표가 구체화될 때 추진한다. |

도메인이 달라도 쿠키 인증 자체가 불가능한 것은 아니다. CORS, SameSite, CSRF, 브라우저의 제3자 쿠키 정책과 배포 도메인 구성을 함께 비교해야 한다. 참고: [MDN CORS](https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/CORS).

로컬 MySQL / 운영 PostgreSQL / 테스트 H2는 당시 편의상 선택했다고 설명할 수 있다. 앞으로는 DB 차이로 생기는 실패를 줄이기 위해 로컬과 중요한 통합 테스트를 운영 PostgreSQL에 맞추는 방향을 권한다. JPA가 DB 차이를 없애주지는 않는다.

## 4. 왜 PWA이고, 왜 앱이며, 왜 원스토어인가

세 가지는 서로 다른 결정이다.

| 결정 | 이 프로젝트의 근거 | 검증할 것 |
|---|---|---|
| PWA | 기존 웹을 유지하면서 홈 화면 접근, 설치된 창에서의 사용, 연결이 불안정할 때의 조회 경험을 제공한다. | 지원 기기에서 설치/재실행이 되는지, 캐시가 오래된 일정을 오해하게 하지 않는지, 웹 대비 재접근이 편한지 |
| 설치형 앱 경험 | PC에서는 기록을 정리하고 이동 중에는 오늘의 일정과 면접 정보를 빠르게 확인하는 반복 사용을 지원한다. | 실제 사용 빈도와 동선, 알림을 통해 일정 확인까지 걸리는 과정 |
| 원스토어 배포 | 사용자가 정한 출시 목표이며, 국내 Android 사용자에게 스토어 설치/업데이트 경로를 제공하고 실제 배포·운영 경험을 얻는다. | 목표 사용자가 원스토어를 쓰는지, 설치 전환/업데이트 성공, 심사 대응과 지원 부담 |

원스토어가 사용자 유입을 자동으로 만들어주거나 모든 Android 사용자에게 적합하다고 가정하지 않는다. '다른 스토어가 번거로워서'는 개발자 제약에 대한 보조 이유가 될 수 있지만 사용자 가치에 대한 설명을 대신하지는 못한다.

PWA에서도 Push API와 service worker를 이용해 화면이 열려 있지 않을 때 알림을 받을 수 있다. 따라서 푸시만으로 별도 Android 패키지가 반드시 필요하다고 설명하지 않는다. 설치 지원, 알림 권한, OS/브라우저 지원은 각각 검증한다. 참고: [MDN 백그라운드 동작](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Offline_and_background_operation).

### Android 구현 방식 제안

| 후보 | 선택 근거 | 감수할 비용 |
|---|---|---|
| TWA + Bubblewrap | PWA 경험을 그대로 제공하고 스토어 배포가 주목적일 때 먼저 검증할 후보 | 지원 브라우저에 의존한다. 사이트와 앱의 Digital Asset Links 검증 및 실제 배포 서명 지문 관리가 필요하다. |
| Capacitor | 로컬 알림, 네이티브 공유 수신 등 구체적인 기기 연동 요구가 PWA 검증에서 드러날 때 후보 | WebView/네이티브 플러그인, Android 빌드, 권한, 인증 저장 및 링크 처리를 추가 관리한다. 필요한 플러그인의 실제 지원 범위를 확인해야 한다. |
| 별도 네이티브 UI | 웹으로 충족하기 어려운 핵심 경험이 확인될 때 재검토 | 현재 React 화면을 다시 만드는 개발/유지 비용이 크다. 현재 요구에서는 우선순위가 낮다. |

TWA는 웹 콘텐츠를 사용자의 브라우저로 렌더링하며 사이트와 앱의 소유 관계를 검증한다. Capacitor는 웹 프로젝트에 네이티브 런타임과 플러그인 접근을 더한다. [Chrome TWA 공식 문서](https://developer.chrome.com/docs/android/trusted-web-activity), [Capacitor 공식 문서](https://capacitorjs.com/docs).

원스토어의 공개 문서는 APK/AAB 등록과 앱 서명 절차를 안내한다. TWA나 Capacitor로 만들었다는 사실만으로 해당 상품의 심사 승인이 보장되지는 않는다. 출시 시 최신 가이드, 대상 Android 버전, 패키지명, 서명 키, 등록 자료와 실제 기능을 함께 점검한다. AAB로 전환한 상품은 APK로 되돌릴 수 없다는 공식 안내도 있어 최초 형식 선택을 기록한다. [앱 서명 안내](https://onestore-dev.gitbook.io/dev/tools/tools/app-signing), [상품 FAQ](https://onestore-dev.gitbook.io/dev/help/faq/apps), [검증 가이드라인](https://onestore-dev.gitbook.io/dev/docs/review/one-store-review-guideline).

## 5. 출시 전에 우선 확인할 실사용 문제

정적 검토에서 확인한 동작과, 실행 검증이 필요한 위험을 구분한다.

1. **로그인 만료가 빈 데이터처럼 보일 수 있다.** 토큰 만료는 1시간이고, `store/auth.js`는 토큰 존재만 확인한다. 공통 응답 처리 없이 홈/알림/캘린더에서 조회 오류를 삼킨다. 만료, 통신 실패, 실제 빈 목록을 구분하고 재로그인 후 돌아갈 경로를 정한다.
2. **지원 기록을 만든 회원의 탈퇴가 실패할 가능성이 높다.** `MemberService.java:53`은 회원만 삭제하고, `Application.java:18`에는 회원 FK가 있다. 자식 삭제/cascade는 보이지 않는다. 기존 탈퇴 테스트는 지원 기록이 없는 회원만 다룬다. 운영 DB에 별도 cascade가 있는지는 미확인이다. 지원 생성 후 탈퇴를 실제 DB에서 검증하고 삭제 정책을 구현한다.
3. **현재 알림은 상태와 면접 시간을 반영하지 않는다.** `utils/notifications.js`는 종료 상태를 제외하지 않고 날짜만 계산한다. 이미 지원한 공고의 마감 알림, 취소된 면접, 당일 이미 끝난 면접을 어떻게 처리할지 도메인 규칙을 정한다.
4. **운영 스키마 변경이 자동 갱신에 의존한다.** `application-prod.yaml:9`의 `ddl-auto: update` 대신 변경 이력이 있는 마이그레이션과 실제 백업 복원 연습을 준비한다. 도구 도입만으로 데이터 복구가 해결되는 것은 아니다.
5. **비밀번호 변경 후 기존 토큰의 효력이 남는다.** 필터는 서명과 만료를 검증하고, 비밀번호 변경은 해시만 바꾼다. 탈취 대응에 필요한 로그아웃/기기별 세션/전체 폐기 정책을 정한 후 인증 방식을 보완한다. refresh token 추가를 자동 정답으로 삼지 않는다.
6. **서버 입력 규칙이 화면 규칙보다 약하다.** 날짜 관계는 프론트에서 검사하지만 요청 DTO에는 같은 검증이 없다. 메모 DB 길이 1000과 API 입력 길이도 맞춘다. 합리적인 날짜 예외는 실제 구직 흐름을 보고 정한다.
7. **PWA가 현재 실패 상태를 캐시하지 않도록 설계해야 한다.** 정적 리소스, 개인정보, 인증 응답을 같은 방식으로 캐시하지 않는다. 로그아웃/계정 전환 때 이전 사용자 데이터가 남지 않도록 검증한다. localStorage 토큰 저장은 스크립트가 읽을 수 있다는 성질을 인증 설계에서 고려한다.

추가로 `SecurityConfig`의 `https://*.vercel.app`은 운영 프론트의 정확한 origin 중심으로 좁힐 수 있다. 이는 허용 범위 정리이며, 이 설정만으로 이미 데이터 유출이 발생했다고 판단한 것은 아니다.

원본 ZIP에는 secret 설정 파일과 환경 파일이 포함돼 있다. 값을 출력하거나 검토 사본에 복제하지 않았다. 앞으로 공유본에는 해당 파일과 Git 이력/빌드 산출물을 제외하는 편이 좋다. ZIP 포함 자체만으로 외부 유출이나 현 키의 유효성을 단정하지 않는다.

## 6. 단계별 발전안과 완료 기준

### A. 신뢰할 수 있는 현재 서비스

- 위 로그인/탈퇴/알림 규칙을 먼저 다듬고 실제 실패 사례를 테스트로 남긴다.
- 로컬 PostgreSQL과 운영에 가까운 통합 테스트, 스키마 마이그레이션, 백업/복구 절차를 준비한다.
- 프론트 lint/build와 핵심 사용자 흐름 검증을 CI에 포함하고, 테스트가 배포를 실제로 막는지 확인한다.
- 완료 기준: 가입 -> 기록 생성 -> 수정 -> 만료/재로그인 -> 재조회 -> 기록 보유 회원 탈퇴가 통과한다. API 실패 화면은 빈 목록과 다르며, 복구한 DB에서 기록을 재조회한다.

Flyway는 적용한 스키마 변경을 버전과 checksum으로 추적하기 위한 후보다. Testcontainers는 PostgreSQL 환경에서 FK/쿼리/마이그레이션을 검증하기 위한 후보다. 단위 테스트까지 모두 DB 컨테이너로 바꾸지는 않는다. [Flyway 버전 마이그레이션](https://documentation.red-gate.com/fd/versioned-migrations-273973333.html), [Testcontainers PostgreSQL](https://java.testcontainers.org/modules/databases/postgres/).

### B. PWA로 반복 사용 경험 완성

- manifest와 설치 아이콘, standalone 표시, service worker의 갱신/캐시 정책을 구현한다.
- 첫 단계는 앱 기본 화면과 사용자가 허용한 최근 일정의 오프라인 읽기로 제한한다. 개인정보를 저장하지 않는 오프라인 안내만 제공하는 더 작은 단계도 가능하다.
- 마지막 동기화 시각과 오프라인 상태를 표시한다. 오프라인 수정/동기화는 충돌과 중복 저장 문제를 추가하므로 별도 요구로 다룬다.
- 현재 PC의 고정 휴대폰 프레임은 실제 작업에 맞는 반응형 화면으로 개선한다. 모바일에서는 키보드, 뒤로가기, 안전 영역, 외부 공고 링크를 검증한다.
- 완료 기준: 실기기 설치/재실행, 네트워크 끊김, 새 버전 갱신, 로그아웃 후 캐시 격리, 긴 회사명과 작은 화면에서도 핵심 동작이 통과한다.

### C. 중요한 일정을 챙기는 알림

- 먼저 '지원예정의 마감', '활성 면접의 시작', '사용자가 선택한 사전 알림 시간'을 정의한다. 날짜만 있는 마감에 임의의 정확한 종료 시각을 부여하지 않는다.
- 초기에는 기존 Spring 서비스 안에서 DB에 알림 예약/구독/발송 상태를 저장하고 주기적으로 만기 작업을 처리하는 구성을 검토한다. 프로세스 메모리에만 타이머를 두지 않는다.
- 일정 변경/취소 시 예약 갱신, 재시작 후 재처리, 재시도, 구독 만료, 중복 억제를 설계한다. 동일 이벤트/수신처/예약 시각을 식별할 키와 처리 상태를 남긴다.
- 푸시 제공자의 접수 성공과 실제 기기 수신을 구분한다. 네트워크와 OS에 따라 지연될 수 있어 정확한 정각 도착을 약속하지 않는다. 재시도 과정의 중복도 절대 없다고 보장하지 않는다.
- 완료 기준: 앱을 닫은 기기에서 수신, 권한 거절 상태, 일정 변경/삭제, 서버 재시작, 실패 재시도, 알림 클릭 후 해당 기록 이동을 검증한다.
- 1차 시간대는 Asia/Seoul 지원을 명시하고 날짜와 순간 시각의 변환 기준을 정한다. 다중 시간대는 실제 사용자 요구에 따라 확장한다.

### D. 원스토어 출시와 운영

- PWA 실기기 검증 결과를 근거로 TWA/Capacitor 방식을 결정하고 그 이유를 기록한다.
- 실제 배포 서명, 버전 증가, 설치 및 업데이트 시 데이터/로그인 유지, 링크와 뒤로가기, 알림 권한을 검증한다.
- 상품 설명/스크린샷/지원 연락처/데이터 처리 안내를 준비하고 최신 스토어 요구사항을 확인한다. 회원 탈퇴와 데이터 처리의 실제 동작이 안내와 일치해야 한다.
- 완료 기준: 심사와 설치 경로를 통과하고, 실제 기기에서 초기 설치 및 후속 업데이트를 검증하며, 장애/문의/복구에 대응할 수 있다.

## 7. 추가 기능의 우선순위

| 후보 | 해결할 문제 | 도입 조건 |
|---|---|---|
| 빠른 등록, URL 붙여넣기 | 공고를 옮겨 적는 부담 | 먼저 실제 등록 시간을 관찰한다. URL 저장만으로도 개선되는지 확인한다. |
| 채용 API 가져오기 | 반복 입력과 오탈자 | 사용자에게 필요한 공고 범위와 승인/이용 조건이 확인될 때. 수동 등록은 계속 지원한다. |
| 여러 면접 및 전형 이력 | 1차/2차 면접을 덮어쓰는 문제 | 해당 흐름이 반복될 때 `ApplicationEvent` 같은 별도 모델을 설계한다. 단순 상태 로그와 실제 예정 이벤트를 구분한다. |
| CSV 내보내기 | 기록 이동과 개인 보관 | 저장한 기록을 사용자가 소유하고 옮길 필요에 대응한다. 백업/복구와는 목적이 다르다. |
| TypeScript | 상태명/nullable 날짜/API 응답 변화로 생기는 화면 오류 | API 모델과 날짜/상태 로직부터 점진 전환한다. 런타임 입력 검증을 대신하지 않는다. [공식 이전 가이드](https://www.typescriptlang.org/docs/handbook/migrating-from-javascript.html) |
| 목록 서버 검색/페이지 처리 | 기록 증가에 따른 응답 크기와 화면 지연 | 사용자별 데이터 수와 측정 지연이 현재 클라이언트 처리를 어렵게 할 때 |
| Docker/EC2 | 실행 환경 재현과 운영 통제 또는 구체적 운영 학습 | 기존 배포와 비용/복구/운영 시간을 비교한다. 셀프 호스트 CI 러너까지 반드시 필요한 것은 아니다. |

Redis, Kafka, Kubernetes, 마이크로서비스, AI 추천은 현재 코드에서 확인된 문제를 해결하는 우선 도입 대상으로 보이지 않는다. 알림량, 처리 지연, 운영 요구가 측정되면 다시 검토한다.

## 8. 검증과 포트폴리오 기록

처음에는 본인 사용 기록과 소수 사용자 관찰로 충분하다. 목표 수치는 기준치를 측정한 뒤 정한다.

- 제품: 지원 하나 등록하는 시간, 일정 확인/변경 성공 여부, 입력 포기 이유, 실제 놓친 일정과 원인.
- 품질: 저장 실패, 로그인 만료 복구, 데이터 손실, 알림 예약/처리 지연, 실기기 수신 결과.
- 운영: 월 비용, 배포 실패, 복구 소요 시간, 업데이트 성공.

취업 준비 서비스는 취업하면 사용이 줄어들 수 있다. 무조건 장기 체류를 성공으로 삼기보다 구직 기간 중 반복 사용과 필요한 일정 관리의 성공을 본다.

기술마다 '문제 -> 대안 -> 선택 -> 감수한 비용 -> 검증 -> 변경 조건'을 남긴다. 예를 들어 '푸시를 구현했다'보다 '앱을 닫으면 일정 알림이 없어서 놓쳤고, 예약을 DB에 저장해 재시작 후에도 처리하도록 바꿨으며, 일정 변경/재시도까지 검증했다'가 더 강한 설명이다. 아직 검증하지 않은 성과와 수치는 작성하지 않는다.

다음에 확인할 미정 사항은 최신 코드 위치, 희망 직무의 비중, 실제 사용 기기, 운영 예산, 원스토어를 통한 대상 사용자 접근 방식이다. 현재 제안은 이 답변 없이도 시작할 수 있는 신뢰성 개선에 우선순위를 둔다.
