# 취준노트 구현 순서와 완료 기준

상태: 2026-09-23 구현 전 제안. 기준 코드 `5775d25`. 상세 계약은 [설계서](IMPLEMENTATION_DESIGN.md)를 따른다.

## 1. 진행 방식

한 번에 하나의 사용자 흐름을 끝내고 다음으로 넘어간다. 각 작업에서 문제/대안/변경/검증을 기록한다. 아래 PR은 제안 분할이며 GitHub에 생성된 PR/이슈가 아니다. 실제 브랜치는 `codex/` 접두사 등 저장소 합의 규칙을 따른다.

단계가 끝날 때마다 개발자가 직접 동작을 설명하고 실기기에서 확인한다. 동작을 확인하지 못한 부분은 '미검증'으로 남긴다. 일정은 작업 가능 시간을 확인한 뒤 정하며 임의의 출시 날짜를 약속하지 않는다.

## 2. 단계와 개발 묶음

| 순서 | 사용자에게 생기는 결과 | 개발 묶음 | 완료 기준 | 선행 |

| 0 | 현재 동작의 기준점 확보 | 로컬/운영 구성 조사, 기존 테스트 실행, 재현 목록 | 기존 실패와 새 변경으로 생긴 실패 구분, 실제 개발 경로 결정 | 없음 |

| 2 | 기록이 있어도 탈퇴할 수 있고 DB를 복원할 수 있음 | PostgreSQL 개발/통합 테스트, 탈퇴 FK 재현/수정, Flyway baseline, 복원 연습 | 기록 보유 회원 탈퇴, 타인 데이터 보존, 기존 스키마 재현/복원 | 0 |
| 3 | 로그인 유지와 확실한 로그아웃 | staging 동일 origin proxy 검증 -> v2 세션/CSRF/전체 폐기 -> 화면 연결 | 쿠키 지속, CSRF 거부, 구 세션 거부, 두 계정 CDN 캐시 격리 | 1,2 |
| 4 | 1차/2차 면접을 별도로 관리 | 일정 모델/v2 API/상세 편집을 함께 구현, version 충돌 | 여러 면접 생성/수정/취소, 이전 데이터 비교, 동시 수정 409 | 2,3 |
| 5 | 홈 요약 박스에서 필터된 지원 목록으로 이동하고 월간 달력에서 일정 확인 | dashboard 집계/목록 view 필터/events API, 월간 UI, 반응형 목록/상세 | 박스 수와 고유 지원 수 일치, 복수/지난/취소 면접 필터, URL 복원, 월 경계/시간 미정 검증 | 4 |
| 6 | 휴대폰에서 설치하고 다시 열 수 있음 | manifest/SW/아이콘/업데이트 안내/오프라인 안내 | S25 Ultra 설치·재실행·입력 중 업데이트·딥링크 새로고침 | 3,5 |
| 7 | 사용자가 켠 기기로 테스트 알림을 받음 | VAPID/구독 API/SW push·click/알림 설정 UI | 수신·클릭, 권한 거절/재허용, A->B 전환, endpoint 검증 | 6 |
| 8 | 앱을 닫아도 예정된 알림을 받음 | job/delivery/worker/재시도/수정 취소, 운영 관측 | 서버 재시작·동시 worker·취소·실패·만료 테스트 및 실기기 수신 | 4,7 |
| 9 | 안정적으로 새 웹 버전 사용 | staging 검증, DB cutover, v1 종료, 배포 순서 통제 | migration 검증, 재로그인 안내, 구 탭 처리, smoke test | 3~8 |
| 10 | 원스토어용 Android 패키지 설치 | TWA/Bubblewrap/도메인 검증/서명/버전 관리 | 서명 APK 최초 설치와 업데이트, provider/fallback 확인 | 6~9 |
| 11 | 실제 원스토어에서 설치 및 피드백 가능 | 상품 자료, 데이터 안내, 최신 검증 기준 점검, 출시 | 심사 통과, 설치 경로 확인, 지원/복구 절차 실행 가능 | 10 |

단계 3~8은 staging에서 점진적으로 검증한다. 실제 사용자에게 부분 제공할 때는 v1/v2 쓰기 경로가 같은 데이터를 다르게 변경하지 않도록 기능 공개 시점을 제어한다. 인증과 일정의 최종 cutover는 상세 설계의 쓰기 점검 절차를 따른다.

### 첫 세 작업의 파일 범위

| 작업 | 주로 바꿀 기존 파일 | 추가할 검증 |
|---|---|---|
| 실패 표시/로그인 만료 | `frontend/src/api/client.js`, `store/auth.js`, `components/layout/PrivateRoute.jsx`, `pages/HomePage.jsx`, `CalendarPage.jsx`, `NotificationsPage.jsx` | 만료/서버 500/오프라인/실제 빈 목록 각각 다른 상태 |
| DB/탈퇴 | `backend/build.gradle`, `src/main/resources/application*.yaml`, `service/MemberService.java`, `repository/ApplicationRepository.java`, 테스트 | 실제 PostgreSQL에서 자식 기록 삭제, 다른 회원 데이터 유지, 빈/기존 DB migration |
| 세션 전환 | `config/SecurityConfig.java`, `controller/MemberController.java`, `security/*`, 프론트 API/auth, `frontend/vercel.json` | cookie/CSRF/session 폐기/프록시 경로/CDN 개인 응답 격리 |

JavaScript->TypeScript는 위에서 수정하는 API/auth와 새 일정 모델부터 시작한다. 색상/레이아웃 전체 개편과 프레임워크 교체를 함께 하지 않는다.

## 3. 단계별 포트폴리오 자료

| 단계 | 남길 설명과 증거 |
|---|---|
| 0~2 | 실제 실패 재현, 왜 H2만으로 부족했는지, FK/복구 결과 |
| 3 | JWT와 세션 비교, 브라우저 배포 조건, 즉시 폐기와 CSRF 테스트 |
| 4~5 | 지원과 일정의 분리 이유, 여러 면접·시간 미정·동시 수정 예시 |
| 6 | 웹/PWA 차이, 캐시 범위를 좁힌 이유, 업데이트 중 입력 보호 |
| 7~8 | Push 접수와 수신의 차이, DB lease/retry/cancel 설계, 장애 실험 |
| 9~11 | 기존 데이터 보존, TWA 선택 이유, 서명/설치/업데이트/심사 경험 |

학습 기록 형식: '내가 설명할 수 있는 동작' 3~5문장, 관련 코드, 실패한 실험 하나, 선택하지 않은 대안과 이유. AI가 작성한 초안과 본인이 검증/결정한 부분도 구분한다.

## 4. 실기기 검증표

기본 기기: Galaxy S25 Ultra. 테스트 당일 Android/One UI, Chrome, 삼성 인터넷, 원스토어 버전과 실제 TWA provider를 기록한다.

| 환경 | 반드시 확인할 동작 |
|---|---|
| Chrome 일반 탭 | 로그인/폼/링크/알림 권한, 새로고침 |
| 삼성 인터넷 일반 탭 | 핵심 폼/날짜 입력/링크, PWA·Push 지원 여부와 제한 기록 |
| 설치된 PWA | 콜드 스타트, 로그인 유지, 뒤로가기, 설치 아이콘, 업데이트, 오프라인 안내 |
| 원스토어용 TWA | Digital Asset Links, 브라우저 fallback, 권한, 서명 APK 업데이트 |
| 화면 꺼짐/절전 | 정상/지연/미수신 구분, 사용자 설정과 테스트 조건 기록 |
| 다른 계정/여러 탭 | 이전 계정 데이터/알림 노출 없음, 로그아웃 전파 |

작은 화면/데스크톱 반응형은 Playwright로 추가 확인한다. 실제 기기 한 종류의 통과를 모든 Android 기기의 호환성으로 표현하지 않는다.

## 5. 운영 준비와 아직 필요한 결정

확정된 사용자 정보: EC2 미착수, 월 예산 미정, S25 Ultra 보유. 현재 설계는 이를 반영했다.

| 결정 | 결정 시점 | 기본안 / 필요한 확인 |
|---|---|---|
| 실제 개발 폴더 | 단계 0 | 현재 clone은 검토용. 사용자의 기존 로컬 변경 여부를 확인하고 작업 기준을 정함 |
| 운영 DB 존재/버전/시간대 | 단계 0~2 | 실제 DB 조회와 백업. ZIP/문서로 추측하지 않음 |
| 공개 origin | 단계 3 이전 | HTTPS origin 하나를 고정. 도메인 소유·쿠키·TWA 검증 가능해야 함 |
| 운영비 | 알림 상시 운영 전 | 플랫폼별 실제 상시 실행/DB/백업/트래픽/도메인 합계 비교 |
| AWS 이전 | 운영비 비교 이후 | 제품 출시의 필수 조건으로 묶지 않음. 비용/운영 학습 효과로 별도 ADR |
| 계정 복구 | 공개 사용자 모집 전 | 초기 제한 안내 또는 검증된 복구 수단 추가를 결정 |
| 원스토어 계정/등록 조건 | 패키지 작업 전 | 최신 개발자센터 조건과 제출 자료 확인 |
| 개인정보 안내/백업 보존 | 베타 사용자 데이터 수집 전 | 실제 저장·삭제·알림·백업 동작과 일치시킴 |

이 결정들은 설계 중 코드 작성 권한을 요청하는 항목이 아니다. 구현 또는 실제 운영으로 넘어갈 때 필요한 입력이다.

## 6. 첫 출시 후 판단

본인과 소수 사용자에게 실제 기록을 입력하게 하고, 등록 시간/입력 포기 이유/알림 유용성/일정 누락/오류를 기록한다. 사용자 측정은 사전 고지와 데이터 최소화를 전제로 하고 초기에는 수동 기록으로 시작할 수 있다.

- 입력 부담이 크면 URL 빠른 등록과 채용 API를 검토한다.
- 오프라인 조회 요구가 반복되면 계정별 로컬 저장과 만료/삭제 정책을 별도로 설계한다.
- 네이티브 공유 수신/로컬 알림이 핵심이면 TWA 대신 Capacitor를 검증한다.
- 목록 지연이 관찰되면 서버 검색/페이지 처리와 인덱스를 조정한다.
- 알림 worker 부하가 API를 방해하면 별도 worker 프로세스로 분리한다. 메시지 브로커 도입은 그 이후 측정으로 판단한다.

출시는 끝이 아니라 검증 가능한 운영의 시작이다. 다운로드 수뿐 아니라 구직 기간에 실제로 기록을 유지하고 필요한 일정을 확인했는지 평가한다.
