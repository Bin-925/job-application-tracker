## 확인한 동작

- 실제 PostgreSQL의 새 DB에서 Flyway V1~V3와 Hibernate validate를 거쳐 서버를 실행했다.
- 로그인 세션과 CSRF를 유지한 조회/등록/내용 수정/상태 변경/복수 일정 추가·수정·삭제/지원 삭제가 반복 부하에서 통과했다.
- 인증 없는 접근, CSRF 누락, 남의 지원·일정 변경, 잘못된 입력, 32KiB 초과 본문을 각 기대한 HTTP 상태로 차단했다.
- 지원과 일정의 오래된 버전으로 덮어쓰는 요청이 409로 거부됐다. 지원 내용이 승자 값으로 남는 것도 확인했다.
- 모든 기기 로그아웃과 비밀번호 변경으로 기존 세션이 무효화됐고, 현재 로그아웃과 탈퇴 후에도 재조회가 거부됐다.
- 기본 요청 제한 프로필에서 429 **43건**을 관측했다. 가입·계정별 로그인·IP별 로그인·CSRF 요청 제한과 Retry-After, IP 예산 회복을 확인했다.
- 경쟁 수정 프로필에서 PUT 1,094건 중 **953건은 409, 141건은 200**이었다. 실제로 다른 값을 저장한 성공 요청은 버전이 증가했다. 충돌 응답은 데이터 손상이 아니라 오래된 수정의 거절이다.
- 목록 조회만 분리한 p95는 일반 사용 12.73ms, 계정당 500개 지원에서 32.63ms였다. 전체 목록 구조의 데이터 증가 영향을 보여주지만 두 실험의 VU 수도 달라 순수한 데이터량 효과만 분리한 비교는 아니다.

## 실행 중 수정한 테스트 오류

실패를 지우거나 통과 기준을 느슨하게 만들어 숨기지 않았다.

1. 최초 H2 점검에서 일정 생성/삭제의 기대 상태를 200으로 적은 테스트 오류를 발견했다. 컨트롤러 계약인 생성 201, 삭제 204로 고쳤다. 이후 Docker가 준비되어 PostgreSQL로 전환했다.
2. 첫 경쟁 수정 테스트에서 같은 VU가 같은 값을 반복 저장해도 버전이 늘어야 한다고 검사하여 실패했다. JPA는 바뀐 내용이 없으면 UPDATE/버전 증가를 하지 않을 수 있다. VU 번호와 반복 번호를 포함해 매번 다른 값을 저장하도록 수정하고 다시 실행했다. 409/버전 증가 임계값을 제거하지 않았다.

이번 실행에서 제품 코드를 수정해야 하는 결함은 확인하지 못했다. 이는 결함이 전혀 없다는 뜻은 아니다.

## 해석과 다음 단계

이 부하 범위에서는 지연 목표를 넘지 않았으므로 Redis나 캐시를 성급히 추가할 근거는 없다. 최고 수용량/포화점은 탐색하지 않았다. 30 VU 통과를 동시 접속 가능한 최대 인원이나 운영 TPS로 표현하면 안 된다. 로그인은 대부분 미리 준비했고 일반 부하의 인증 요청 예산은 완화했으므로, 동시 로그인 처리량이나 기본 제한 적용 상태의 정상 사용자 경험을 이 숫자로 평가하지 않는다.

배포 예산이 정해진 뒤 운영과 유사한 CPU/메모리·영구 디스크·HTTPS에서 같은 실험을 반복하고, 실제 이용 패턴에 맞는 arrival-rate 실험, 수십 분 이상의 지속 부하, DB 쿼리/연결 대기 시간, 서버 재시작·네트워크 장애를 추가해야 한다. 모바일 UI/PWA 성능은 별도 브라우저·실기기 검증 대상이다.

기존 컨테이너는 변경하지 않았고, 전용 서버와 `jobtracker-load-postgres`는 테스트 후 중지했다. **이 컨테이너는 일반 개발 DB가 아니라 데이터가 사라지는 테스트 DB다.**
